1. Zielsetzung & Systemvoraussetzungen

Ziel dieser Übung ist die Inbetriebnahme einer lokalen Docker-Laufzeitumgebung (Docker Desktop auf Basis von WSL2 unter Windows bzw. Docker Engine), das Erstellen eines minimalistischen Dockerfiles mit zwei Zeilen, das Bauen eines eigenen Container-Images sowie die Ausführung und der Lebenszyklus-Test eines Nginx-Webservers.

  • Host-System: Windows 11 64-Bit mit WSL2 (Ubuntu 22.04 LTS / 24.04 LTS)
  • Container-Engine: Docker Desktop / Docker Engine (WSL2-Integration aktiv)
  • Freier Port am Host: 8081

2. Teil A: Docker Installation & Gegenprobe

Zur Überprüfung, ob der Docker-Daemon aktiv ist und Container ordnungsgemäß herunterladen und instanziieren kann, wurde im Terminal der offizielle Test-Container ausgeführt:

Verständnisfrage 1: Was hat Docker bei „docker run hello-world“ gemacht? Schau den Log an und beschreibe in eigenen Worten, was hier passiert ist.
  1. Kontaktaufnahme: Der Docker-Client im Terminal hat den im Hintergrund laufenden Docker-Daemon (Server) über den Socket kontaktiert.
  2. Lokale Image-Prüfung: Der Daemon stellte fest, dass das Image hello-world:latest lokal noch nicht vorhanden war (Meldung: "Unable to find image 'hello-world:latest' locally").
  3. Pull von Docker Hub: Der Daemon hat das fertige Image aus der zentralen Registry (Docker Hub) heruntergeladen.
  4. Container-Erstellung: Aus diesem Image hat der Daemon einen neuen, isolierten Container instanziiert und gestartet.
  5. Ausführung & Ausgabe: Das im Image hinterlegte Testprogramm wurde ausgeführt und hat den Infotext generiert. Der Daemon leitete den Output an das Terminal des Clients weiter.
  6. Terminierung: Da das Programm seine Aufgabe beendet hatte, wurde der Container anschließend gestoppt (Status Exited).

3. Teil B: Ein Dockerfile mit zwei Zeilen

Für das eigene Image wurde ein neues Verzeichnis ~/erstes-image angelegt. Darin wurde die personalisierte Startseite index.html sowie das Dockerfile erstellt: 

mkdir -p ~/erstes-image && cd ~/erstes-image
echo '<h1>Hallo von DEIN-NAME, 5BHWII</h1>' > index.html

Inhalt der Datei Dockerfile

FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
Verständnisfrage 2: Was ist ein Basisimage, und warum musst du nginx nicht selbst im Container installieren?
Ein Basisimage (Base Image), definiert über die FROM-Direktive, bildet das Ausgangsfundament, auf dem ein Docker-Image aufbaut.

Das verwendete Basisimage nginx:alpine beinhaltet bereits ein minimales, voll funktionsfähiges Linux-Betriebssystem (Alpine Linux) sowie einen fertig vorinstallierten, konfigurierten Nginx-Webserver samt dessen Startroutinen. Man muss Nginx daher nicht selbst manuell installieren (z. B. per apk add nginx), weil die Entwickler des Basisimages dies bereits getan haben. Man baut direkt auf diesem geprüften Baustein auf und muss lediglich seine eigene Webdatei per COPY an die richtige Stelle kopieren.

Das Image wurde anschließend mit Tag 1.0 gebaut und aufgelistet:

docker build -t erstes-image:1.0 .
docker images

Verständnisfrage 3: Warum steht am Ende von docker build ein Punkt, und was passiert, wenn du den Befehl aus einem anderen Ordner startest? (statt Punkt ein anderer Directory/Pfad)
Der Punkt (.) definiert den Build-Kontext (Build Context) und teilt Docker mit: "Verwende das aktuelle Verzeichnis als Wurzelverzeichnis für den Build". Docker sucht dort nach dem Dockerfile und allen im Buildprozess referenzierten Dateien (wie index.html).

Startet man den Befehl aus einem anderen Verzeichnis, muss man den relativen oder absoluten Pfad zu diesem Ordner angeben (z. B. docker build -t erstes-image:1.0 ~/erstes-image). Lässt man den Pfad ganz weg, schlägt der Befehl fehl (Syntaxfehler). Gibt man einen Ordner an, in dem kein Dockerfile oder die benötigten Dateien liegen, bricht der Build mit Fehlern wie "failed to read dockerfile" oder "COPY failed: file not found" ab.

4. Teil C: Container-Betrieb & Lebenszyklus

Der Container wurde im Hintergrundmodus (-d) mit Namen web1 gestartet. Dabei wurde Port 8081 des Laptops auf Port 80 des Containers weitergeleitet: 

docker run -d --name web1 -p 8081:80 erstes-image:1.0
docker ps

Verständnisfrage 4: Welche der beiden Zahlen in -p 8081:80 gehört zu deinem Laptop, welche zum Container?
Die Syntax lautet -p <Host-Port>:<Container-Port>:
  • 8081 gehört zum Laptop (Host): Auf diesem Port lauscht das Betriebssystem des Laptops. Wenn wir im Browser http://localhost:8081 aufrufen, spricht der Browser diesen Host-Port an.
  • 80 gehört zum Container: Das ist der interne Port innerhalb des isolierten Container-Netzwerks, auf dem der Nginx-Webserver standardmäßig lauscht.
Docker sorgt für das Routing und leitet Anfragen vom Host-Port 8081 an den internen Container-Port 80 weiter.

4.1 Hineinschauen & Logs

docker logs web1
docker exec web1 cat /usr/share/nginx/html/index.html

docker logs zeigt die HTTP-Zugriffslogs (Status 200 bei Browser-Aufruf). Mit docker exec lässt sich ein Befehl direkt im Container ausführen, womit der tatsächliche Inhalt der Datei im Container verifiziert werden konnte.

4.2 Seite ändern & Version 1.1

echo '<h1>Hallo von DEIN-NAME, Version 2</h1>' > index.html
docker build -t erstes-image:1.1 .
Verständnisfrage 5: Du hast index.html geändert, der Browser zeigt trotzdem die alte Seite. Erkläre kurz warum, nutze die Wörter Image und Container.
Ein Image ist eine unveränderliche (immutable) Schablone. Die ursprüngliche index.html wurde beim Bauen fest in das Image erstes-image:1.0 hineinkopiert.

Der laufende Container web1 ist eine isolierte Instanz, die zur Laufzeit auf diesem unveränderten Image basiert.

Eine nachträgliche Bearbeitung der Datei index.html auf dem Host-Dateisystem berührt weder das bestehende Image noch den bereits aktiven Container. Erst wenn man aus den geänderten Dateien ein neues Image (z. B. Version 1.1) baut, den alten Container stoppt/entfernt und einen neuen Container auf Basis des neuen Images instanziiert, wird die neue Version der Webseite ausgeliefert.

4.3 Neue Version starten und Aufräumen

# Alten Container entfernen und Version 1.1 starten
docker rm -f web1
docker run -d --name web1 -p 8081:80 erstes-image:1.1

# Nach Überprüfung aufräumen
docker rm -f web1
docker ps -a
docker images

5. Vertiefung / Zusatzaufgabe Optional

1. Schichten-Analyse mit docker image history erstes-image:1.1:

Die Ausgabe veranschaulicht das Layer-Prinzip von Docker: Die unteren Schichten stammen unverändert aus dem Basisimage nginx:alpine (OS-Binaries, Nginx-Installation). Unsere COPY-Anweisung bildet die oberste Schicht (wenige Bytes), wodurch der Speicherbedarf für Folgeversionen minimal bleibt.

2. Inspektion des Alpine-Linux Minimal-Systems:

docker run -it --rm alpine sh
/ # ls /
/ # cat /etc/os-release
/ # exit

Alpine Linux verzichtet auf Ballast, setzt auf musl libc und BusyBox und ist nur rund 5 MB groß, bietet aber eine vollständige POSIX-Umgebung. Der Parameter --rm sorgt für das automatische Löschen des Containers beim Beenden.

6. Zusammenfassung & Fazit

In dieser Praxisübung wurden die fundamentalen Konzepte moderner Cloud- und Container-Architekturen erfolgreich demonstriert:

  • Deklaratives Setup: Ein Dockerfile definiert reproduzierbar die exakte Laufzeitumgebung.
  • Immutability: Images sind schreibgeschützt, was unkontrollierte Konfigurationsdrifts verhindert.
  • Port- und Prozess-Isolation: Container laufen isoliert vom Hostsystem und kommunizieren ausschließlich über definierte Ports und Schnittstellen.
